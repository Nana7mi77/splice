# 尚未解决的问题与可能的反例

首版的价值是将主张变成可观察的局部实验。以下问题不因演示通过而自动得到解决，也不应全部变成首发前置工程。

## 意图、语义与组合

**从未见过的能力能否被正确使用？** `x-fact` 和输入输出 Schema 降低了结构绑定难度，却没有解决单位、时间范围、估值口径和隐含条件。未来应让模型面对未出现在解析样本中的插件，分别度量召回、版本选择、填参和拒绝错误调用的质量。新增 Manifest 能被简单检索到，只证明索引接纳能力，不证明模型理解其全部语义。

**目标如何分解，多个候选如何选择？** 首版允许有限的事实依赖计划。多个插件输出相同事实时，质量、价格、权限、版本和数据新鲜度都可能冲突。复杂分支、循环、长程依赖、补偿和部分失败需要更强的规划模型。不能在 CLI 中增加越来越多的场景分支，同时仍宣称组合是通用的。

**JSON 合法是否意味着业务正确？** 不是。金额可以结构合法但单位错误，余额可以来自错误月份，资产估值可以过期。需要在普通结构约束之外研究可验证的语义契约、来源和新鲜度。模型不确定性应在提出参数、候选和计划时显露，最终执行权限与状态约束必须独立确定。

## 执行边界会不会退化为旧服务层

**什么属于 Manifest、Runtime 原语或专用服务？** 简单筛选、聚合和价格计算适合声明化；外部支付承诺和严格时延任务可能需要确定性服务。界线应按复用、可解释性、性能与状态责任判断，不能以“零业务代码”为目标牺牲正确性。

**如何发现 Gateway 膨胀？** 观察每新增一个能力时，是否增加插件 ID 分支、专用函数和跨域工作流；同时统计新增可信资源规则。若扩展主要发生在 Gateway 而非声明中，可能只是把传统后端换了入口。已有网关包含草稿与价格的资源约束，不能把这些预置知识从成本账上抹去。

**何时缓存或编译？** 高频且稳定的请求可能不值得反复规划。应比较动态发现、计划缓存和编译执行的成本，以及权限、数据契约或插件版本变化时如何失效。生成固定服务可以是优化产物，不代表必须回到全部人工预编写的生产方式。

## 外卖与资产的特殊语义

**最小共享能否覆盖真正的跨域需求？** 预算判断和允许限额可以支持简单消费约束；复杂家庭预算可能还需要账户归属、限制用途或未来现金流。应按目标提供最少事实，而非把原始账本传给消费插件。日志、错误信息和执行轨迹也可能泄露金融明细，不能只审查正常返回值。

**现金、持仓与预算如何避免混用？** 现金余额、投资估值和餐饮预算是不同概念。估值快照可能陈旧，现金也可能有冻结金额。首版虚构数据没有完整结算、冻结和流动性模型，因此只能演示定义范围内的预计可用金额。

**多笔拟消费如何处理？** 本地草稿不预占预算、不扣减现金；两个草稿可能各自通过同一份余额检查，合计却超出预算。若未来真正承诺消费，需要预占、并发控制、过期、撤销和外部一致性。当前草稿事务只保证本地写入行为，不保证跨系统财务一致性。

## 权限、来源与运行环境

**谁有资格发布一个金融插件？** 声明领域或权限不等于具备可信身份。首版本地受控示例不解决第三方签名、供应链、来源认证、撤销和多租户授权。真实发布系统必须防止插件通过自报身份扩大资源访问范围。

**模型和插件描述能否越过边界？** 描述内容可能诱导参数填充和能力选择，输出也可能伪装成后续指令。结构化解释器缩小执行面，但不能据此声称任意第三方插件都安全。需要独立检查数据流、资源策略和用户授权，并对误导性契约开展针对性实验。

**离线和不同手机硬件意味着什么？** 插件索引、Schema 和模型需要占用存储与内存；离线设备可能只有旧版本和旧事实。应测量端侧延迟、耗电、失败处理及隐私影响，而非仅凭本地 CLI 就声称真机可用。

## 领域 LoRA / Adapter 热插拔

这是明确保留的后续研究方向，不是首版训练任务。

- 通用模型如何在加载 Adapter 之前判断领域？是否先用通用检索得到候选，再决定加载？
- Adapter 应强化哪些任务：专业意图结构化、Query Rewrite、插件召回与重排，还是专业知识检索？如何分别测量改善？
- 跨领域任务需要同时加载多个 Adapter，还是轮流处理并共享结构化事实？如何避免一种领域语义覆盖另一种？
- 不同模型基座、量化方式、推理框架与 Adapter 版本如何兼容？冷加载、常驻和卸载的内存与时延代价多大？
- 服务侧 Harness 能否产生可靠训练数据？如何控制合成数据错误、领域偏置和动态插件索引过期？
- 领域级适配能否覆盖多个独立插件，而不退化为“每插件训练一个执行模型”？

无论结果如何，LoRA 都不能替代 Registry 的真实能力索引、动态 Schema 或 Gateway 的权限规则。

## 产业命题如何被反驳

如果能力验证、集成与长期维护成本持续高于专用服务，或者平台入口与真实资源无法开放，意图消费可能长期只是既有 App 的辅助层。如果用户倾向明确可见的固定操作，交互也可能保留较强应用边界。这些结果都应被允许出现。

软件能力采用率、技术可用性与利润分配需要不同证据。原型不能回答岗位数量、SaaS 收入或企业边界的变化；未来讨论应依赖明确的成本和市场观察，并保留平台集中、开放生态与混合架构等竞争性情景。
