# Roadmap

本项目先交付一个可以运行和被反驳的局部实验。阶段划分表达研究顺序，不代表时间承诺；P2 项目均未因列入路线图而完成。

## P0：公开主张与可检查边界

交付中文介绍和英文摘要、[思想纲领](THESIS.md)、[架构说明](../ARCHITECTURE.md)、[RFC-0001](../RFC/0001-intent-driven-software.md)、[对照说明](comparison.md)与[开放问题](open-questions.md)。

以 Splice — Composable Service Access for Agents（面向 Agent 的组合式服务访问）为项目定位，明确目标是省去人工预制的专用中间业务 Service，保留底层服务与可信执行边界。区分产业假说、架构命题与原型行为；不把单一组件称为原创，也不据未核实材料评价 Muse 或 DeepSeek 内部实现。明确开源许可与虚构数据来源。

## P1：离线可运行的外卖 × 资产原型

实验路径覆盖点外卖、独立资产概览和预算约束下的跨域订单草稿。四类独立能力通过 Registry 和 Schema 发现与绑定，使用共用解释器、受控数据资源与本地草稿事务。

重点检查契约拒绝、权限拒绝、含配送费约束、现金与持仓区分、预算不足不写入，以及新增或替换声明时不改公共执行路径。Mock 模型、有限意图类型和受限计划表现力应在输出与文档中如实标明。

P1 的成功标准是这些局部行为可观察、可复现，不是构建分布式系统、真实手机工程或训练环境。实际命令和验证结果见 [README](../README.md)。

## P2：真实能力生产与端侧消费

先使生产侧 `CapabilityProducer` 可接入可选 LLM，让模型产生可检查的 Manifest 草稿，保留生成结果与发布契约的边界。再将 `OnDeviceIntentAdapter` 接入真实小模型，评估未见插件的语义发现、输入填充和拒绝错误调用；离线 Mock 仍应能独立运行。

端侧评估需要记录硬件、模型、量化、内存、延迟和耗电，不能只报告单条成功示例。只有出现真实需求时才引入更重的检索基础设施；先度量简单索引的失败。

## P2 专题：领域 LoRA / Adapter 热插拔

通用端侧基座可以按领域动态加载适配器，以增强专业术语和隐含条件理解、意图结构化、Query Rewrite、插件能力召回与重排，以及未来的专业知识检索。这是项目明确的后续研究路线，首版不训练、不加载。

研究顺序如下：

1. 先建立无 Adapter 的真实端侧基线，识别错误来自解析、检索、填参还是执行契约。
2. 选择有多种独立能力的领域，生产领域级数据与适配器，比较同一基座有无 Adapter 的效果；避免每插件一个 LoRA 的强绑定。
3. 研究通用检索与领域路由的先后关系，以及跨领域任务的多 Adapter 协调。
4. 度量热加载、卸载、缓存、基座兼容和量化影响，判断精度增益是否值得资源代价。
5. 研究服务侧 Harness 支持训练数据、适配器构建与版本分发，但不让适配器更新替代动态插件索引更新。

适配器不拥有额外权限，不执行交易，也不作为金融判断的可信来源。它改善提出意图和搜索候选的质量，实际运行仍经过相同 Schema、条件与 Gateway。

## P2：组合、优化与可信分发

扩展能力重叠、版本冲突、计划分支与部分失败的处理；比较动态计划、缓存与自动编译的总成本。记录每新增领域所需的资源适配、原语和专用服务代码，检查 Gateway 是否膨胀为业务流程集合。

第三方能力分发需要来源认证、签名、撤销、细粒度授权、日志脱敏与多租户隔离。预算预占、并发消费和真实业务确认则需要独立的一致性与责任模型。它们是进入真实数据和真实执行前的研究工作，不是本地虚构草稿演示已经提供的保证。

MCP 可作为将来互操作适配器，让现有工具或资源参与能力生态；它不会取代能力生产、版本分发、意图消费与受控执行的分工。
