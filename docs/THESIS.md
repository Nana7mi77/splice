# Splice：面向 Agent 的组合式服务访问

> 状态：公开思想纲领与可检验的架构假说。项目名称为 Splice，完整定位为 Composable Service Access for Agents。本文区分产业推测、架构命题与原型证据，不把其中任何一层当作另一层的证明。

**Agent 按意图组合访问底层服务，无需预制中间业务 Service。** 软件能力可以由智能生产、按意图发现，并由受控运行时执行。完整应用与人工预制的中间业务服务，是否还必须是它们的默认组织形式？

这是 Splice 的起点。项目不预测代码消失；恰恰相反，机器生产的代码、声明和执行计划可能越来越多。我们研究的是，人是否仍须在每一种需求出现之前，亲手设计一套界面、流程与专用服务，并要求用户学会这套软件的操作方式。

## 为什么过去需要预制软件

传统软件把人的需求翻译成一组提前确定的操作。用户想控制开支，却需要先打开财务软件查预算，再打开外卖软件看菜单，最后自己比较两边的信息。这种分工并非毫无道理：自然语言有歧义，机器缺乏可靠的目标理解能力，而提前编写的程序容易重复执行、验证和维护。工程师把行为路径固定下来，实际上是在用开发成本交换执行的确定性。

App、API 和企业内部业务流程也因此成为生产与协作的边界。它们帮助组织分工，却同时要求需求迁就已有的软件切面。预算属于财务，点餐属于消费，用户要完成的日常目标反而被拆成多个产品里的步骤。这里的历史限制是机器理解与执行意图的成本，并非人的目标天然就应被这些产品边界切开。

## 从操作程序到消费能力

如果理解意图、生成软件和验证局部行为的成本持续下降，另一种分工值得尝试：人表达目标和约束；智能系统生产或寻找适合的能力；设备在授权范围内组织这些能力；确定性的执行边界保证最终动作符合数据契约与规则。

“帮我找一份含配送费不超过 30 元的盖饭，不能突破本月餐饮预算，合适就生成草稿”并不是三个彼此独立的 App 请求。它是一个同时涉及偏好、价格、预算、现金和允许动作的目标。用户无需事先知道由哪一个供应商提供菜单、由哪一个插件计算预算。供应商仍然重要，但其价值可以通过资源、事实和可执行能力被消费，不一定要以独占一个屏幕入口的形式体现。

运行时组合也不意味着每次都要从头思考。稳定、高频的组合可以缓存，甚至自动编译成确定性服务。变化在于：是否固定为服务，是经过观察后的执行优化，而不必是每一个新目标进入系统之前的人工开发前提。

## 生产侧与消费侧为何分开

Splice 提议把高成本的能力生产集中在服务侧 Harness：模型理解业务描述，生成版本化插件声明、输入输出契约与受限执行计划，经过检查后发布。终端侧负责更窄的任务：把请求结构化，搜索实际存在的能力，填充参数，并提出可检查的组合。

这是一种成本与职责的假设，不是已经证明的最优部署方式。手机侧模型不需要在每一次点击后复制一整套高成本云端 Agent；生产出的能力可以被多次消费。与此同时，云端生产不会天然带来安全性或正确性，端侧运行也不会天然保证隐私。插件必须有可信的数据来源与执行边界，设备仍须处理模型能力、内存、耗电、离线索引和版本兼容问题。

首版用两个明确标注的 Mock 模拟这些角色：生产侧从受控模板产生 Manifest，终端侧从有限请求类型产生结构化意图。它们使架构实验能离线运行，但不构成大模型自主生产能力或手机模型理解任意中文的证据。

## 省去专用中间业务层，保留可信执行边界

组合式服务访问让 Agent 根据目标组织底层能力，不要求先为每个流程新增一个人工编写的中间业务 Service。底层服务和数据资源仍然提供事实与动作，Gateway 继续约束访问和状态。鉴权、持久状态、事务和审计仍然需要存在。这些确定性约束的必要性，并不能直接推出“每一种业务目标都必须有人工编写的专用后端 Handler”。反过来，开放数据库也不等于拥有了可信执行能力。

Splice 将可组合逻辑放进插件声明，将读取、筛选、投影、聚合、比较、排序、断言和受控插入放进可复用 Runtime 原语，资源关联由受限的 `lookup` 表达式完成。Gateway 保护资源访问与不可违反的状态转移。它不应随着插件数量增长而出现一串 `create_food_order`、`assess_budget` 或跨域大函数。如果每发布一个能力都要新增这种函数，架构就可能只是把传统服务改了名字。

真正应度量的问题是：**在数据契约与受控执行原语已经存在时，一个新业务意图需要多少新增的人工专用服务代码？** 不能只统计插件文件增加了多少，也要计算隐藏在解析器、调度器和网关里的领域分支。某些业务确实需要新原语、供应商适配器或确定性服务；记录这些反例，比声称“零后端”更有价值。

## 连续的生活状态，而非彼此孤立的功能

点外卖与资产管理是这项实验的第一组领域，因为一次小额消费同时改变预算预测、现金余量和之后的选择空间。资产管理也不只是外卖预算的附属字段：现金账户、投资持仓估值、支出与预算本身应能独立被查询和解释。

组合的前提是明确语义与权限。投资持仓估值不等于可支付现金；拟消费后的余额不等于已经记账的余额；订单草稿不等于已提交订单。预算插件可以向终端和组合计划提供授权后的限额、判断与预计余额，外卖插件不应因此获得完整账户与流水。可组合性不是所有插件共享所有信息。

首版通过本地 Runtime 和虚构数据模拟服务访问与组合，尚未连接真实远程底层服务，并且只允许写入本地未提交草稿。它不付款、不提交外卖订单、不转账、不买卖证券，也不接入真实账户。预计预算与现金影响仅是模拟扣减。这个范围足以检查一次跨域数据依赖是否实际成立，无需把支付系统带入第一轮研究。

## 产业含义是竞争性情景，不是结论

如果能力生产和数字协调变得更便宜，通用软件功能的边际供给成本可能下降。企业中依赖固定流程的采购、财务、运营和 IT 分工，也可能因搜索、协调、执行与监督成本的改变而重新组织。但制度责任、信任、资源控制和线下交付不会仅因模型更聪明而消失。

至少存在三种竞争性情景。其一，开放能力市场使小型供应商也能被终端发现，用户入口与资源提供者更易分离。其二，操作系统、支付资格、分发渠道和关键数据的控制者把新能力吸收进平台，议价权反而更加集中。其三，集成和验证成本长期高于预期，成熟 SaaS 与确定性服务继续占优，插件组合只在有限领域补充现有软件。

高资源用户可能先承担推理、试错与集成成本，后来能力才随着成本下降而下放。这只是可观察的采用路径假说，不是大众市场必然按同一形态出现的证明。更不能把采用率等同于利润：即使数亿人使用意图驱动能力，收益也可能更多流向真实业务资源、独占事实、物理生产能力、产权与渠道的控制者，而不是每位插件作者。

## 哪些事实会使这一方向受限

数据语义若不完整，Schema 合法也可能执行错误的目标；权限若不足，系统只能诚实地停下；复杂多步骤任务若依赖长期状态、补偿与外部承诺，简单声明式组合可能远远不够。对于低成本、低变化的业务，预制服务可能一直更快、更便宜、更可靠。

端侧模型也可能无法在小内存和低功耗条件下稳定理解新能力。插件描述可能误导检索，版本冲突可能破坏组合，平台可能阻止开放分发。如果这些成本没有下降，激进的“应用边界弱化”就可能不发生。原型应让失败可见，而非把每个失败都解释为“未来模型会解决”。

## 领域 LoRA 是明确的后续研究方向

手机基础模型未来可以按需加载领域 LoRA / Adapter，增强专业术语理解、隐含约束识别、意图结构化、Query Rewrite、插件召回与重排，并探索专业知识检索。研究单位是一个领域中的多种能力，而不是为每个插件训练一个执行模型。

领域适配器无法替代动态插件索引和真实 Schema，也不承担权限或交易执行的可信边界。需要研究的是何时路由领域、何时加载和卸载、跨域请求如何协调多个 Adapter、不同基座能否兼容，以及精度改善是否值得端侧内存和时延成本。服务侧 Harness 可以未来参与训练数据和适配器生产；这条路线明确保留，但训练与热加载都不是 P0/P1 的前置条件。

## 三层主张与证据边界

| 层次 | 本项目提出什么 | 什么证据才有说服力 |
| --- | --- | --- |
| 哲学与产业假说 | 预制 App 和人工专用服务可能不再是默认的软件组织方式，价值分配可能随之变化 | 长期成本、采用、组织变化与市场分配研究；一个 Demo 无法证明 |
| 可研究的架构命题 | 云端生产、版本分发、端侧意图消费与通用受控执行，可以减少新能力所需的专用服务代码 | 多领域扩展成本、发现与绑定成功率、原语复用率、失败案例及与传统方案的比较 |
| MVP 可观察行为 | 在有限意图与受限声明式计划内，发现独立插件，校验契约，组合虚构外卖与资产能力，受权限约束生成本地草稿 | 可运行命令、执行轨迹、负例与新增 Manifest 实验；以实际运行结果为准 |

这里的 MVP 不是宏观结论的缩小版证明。即使所有演示通过，也不能推出 SaaS 消失、岗位减少、手机已经拥有开放域智能，或生产关系必然重构。它最多为一个更具体的问题提供可复现证据：**当数据与执行边界已经具备时，新发布的能力能否被现有意图接口发现并执行，而无需重建 App 或添加专用业务服务？**

Splice 的价值在于把这个问题变成可以运行、观察和反驳的实验，并准确记录在哪些地方仍需人工、模型或传统服务。
