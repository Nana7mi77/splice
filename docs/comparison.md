# 与既有软件和 Agent 技术的关系

Splice 研究面向 Agent 的组合式服务访问：Agent 按意图组合访问底层服务，无需为每个流程预制中间业务 Service。它组合了已有的插件、声明式执行、Schema、能力检索和权限治理思想。原创性主张局限于所研究的架构分工及其可证伪命题，不主张首次发明任何单项机制，也不声称替代所有 App 或服务。

要比较的是“新业务目标如何进入系统”：需要重新制作一个应用或专用服务，还是能在已有数据与执行边界内，通过新的能力声明被发现、组合和消费。后一条路径是否更便宜、更可靠，需要实验，不能由命名决定。

| 对照对象 | 已有机制解决什么 | Splice 研究的增量问题 | 可共存方式 |
| --- | --- | --- | --- |
| 传统 App / SaaS | 提供稳定入口、业务流程与确定性服务 | 新目标能否减少对预制界面和专用流程的依赖 | App 仍可展示结果，稳定服务仍可承担高频执行 |
| API / Tool Calling | 让程序或模型调用已有能力 | 谁生产和分发能力，动态契约能否支持新目标的发现与组合 | API 可作为受控原语后的供应商适配层 |
| MCP | 通过协议连接模型应用与外部工具、资源及上下文 | 能力生产、版本分发与数据驱动运行能否形成完整生命周期 | 未来将能力导出为 MCP 工具，或受控使用 MCP 资源 |
| Agent Harness | 组织模型、工具、上下文、执行反馈与运行环境 | 高能力模型能否主要用于生产可复用能力，终端承担更窄的意图消费 | Harness 成为生产侧的一部分 |
| Schema-first / 数据驱动应用 | 用契约描述数据或行为，减少重复代码 | 动态发布的契约能否被端侧意图接口正确找到并绑定 | 直接复用 JSON Schema 等成熟基础 |
| Policy enforcement / Gateway | 在可信边界内校验身份、权限与动作 | 保留约束的同时，能否避免网关膨胀为按插件增加的业务后端 | 作为执行必要条件，非本项目独有贡献 |

## 为什么一个工具包装器不足以证明命题

若外卖插件只调用手写的 `order_food_with_budget` 服务，而服务内部完成菜单查询、财务评估和草稿写入，那么插件数量即使增加，核心工作流依然被人工预制。它可以是有用的工程，但没有证明本项目关心的变化。

首版通过本地虚构资源模拟底层服务访问，要求外卖检索、资产概览、预算评估和订单草稿各自具有契约。跨域依赖由 `x-fact` 语义事实与 Planner 连接，执行通过共用解释器和资源策略进行。新增或替换菜单声明后，应继续走同一条发现、绑定与执行路径。

这也不意味着声明式解释器总比专用服务优越。复杂外部承诺、低延迟交易和稳定高频业务可能更适合确定性服务。实验必须把新增原语、数据契约和网关规则的维护成本一起算进去。

## Muse 与 DeepSeek Harness：资料边界

本次原型没有核实足以准确界定 “Meta Muse” 或 “DeepSeek Harness” 内部实现的一手材料，因此不作具体功能、架构优劣或原创性比较，也不推断它们与 Splice 相同或不同。

未来若加入对照，应先注明官方资料链接、版本与发表时间，再逐项比较能力生产、分发、消费和执行的责任划分。没有公开证据的内部设计保持未知。上表中的 Harness 是通用架构类别，不代表对某个厂商产品的断言。
